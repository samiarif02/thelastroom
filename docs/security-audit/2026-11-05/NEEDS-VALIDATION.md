# Needs validation: The Last Room (07a1b30, quick profile)

These are source-grounded leads whose decisive check could not run in this audit, because the host has no OS-enforced sandbox and no target code was executed. They carry **no severity** and are **not confirmed vulnerabilities**. They are listed in the parent's priority order, which ranks by the shared resource affected and how cheap the attack is. Every resolution plan below is either a local sandboxed check using dummy data or a read-only observation by the owner. None of them sends traffic to a deployment.

## 1. Any signed-in player, including a free anonymous guest, can write arbitrary XP and streak values and take over the shared leaderboard

**Fingerprint:** `supabase/migrations/20261104120000_leaderboard.sql:profiles-client-reported-xp-unbounded`

public.leaderboard ranks total_xp, week_xp, week_start and streak_weeks exactly as the owning player stores them. The authenticated role holds column-level INSERT and UPDATE on those columns (leaderboard.sql:38-41). Anyone can get that role through anonymous sign-in (config.toml:188, 30 per hour per IP at :213, captcha commented out at :224) or through an email signup (enable_signup at :186). Owner-only RLS (create_profiles.sql:46-53) only ties the write to the caller's own row. It does not limit the values. The only value checks are total_xp >= 0, week_xp >= 0, streak_weeks >= 0 and week_start being a Monday (leaderboard.sql:31-34). A player can therefore upsert their own profile with total_xp = 2147483647, week_xp = 2147483647, week_start = the current UTC Monday, streak_weeks = 32767 and any first_name of 1-40 characters (sync_profile_and_attempt_picks.sql:14). That puts them at #1 on both the weekly and the all-time board, which public.leaderboard returns to every authenticated caller. The board shows at most 100 rows (leaderboard.sql:101, 148). Enough such accounts (about 100, which the local per-IP anonymous limit spreads over hours per IP) fill the visible top 100, push every honest player off it, and show the attacker's chosen display names to everyone. A future-Monday week_start also passes the streak recency test (117), but this only matters alongside the same root cause. The migration (23-24) and docs/completion.md:33 call client-reported XP a known limit. It is still reported because leaderboard integrity is a protected resource shared by all players and nothing on the server bounds or derives these values. The hosted project's exposure depends on this migration being applied there (docs/completion.md:33 says it still needs applying).

**Claimed root cause:** 20261104120000_leaderboard.sql grants authenticated direct INSERT/UPDATE of the ranked columns (lines 38-41), with only non-negativity and Monday CHECK constraints (31-34). public.leaderboard (SECURITY DEFINER) then ranks those stored values with no server-side recount from mission_attempts, no upper bound and no plausibility or rate-of-change check (115-117, 126, 134).

### Source trace
- **entrypoint**: `supabase/config.toml:188` ([auth] enable_anonymous_sign_ins). enable_anonymous_sign_ins = true: anyone can mint an authenticated-role JWT (30 per hour per IP at line 213; captcha commented out at line 224; email signup is also on at line 186).
- **propagation**: `supabase/migrations/20261104120000_leaderboard.sql:40` (grant update (leaderboard_visible, total_xp, week_xp, week_start, streak_weeks)). authenticated may write the ranked columns of its own profile row directly through PostgREST. The owner-only RLS policies (create_profiles.sql:46-53) bind only the row (auth.uid() = user_id), not the values.
- **propagation**: `supabase/migrations/20261104120000_leaderboard.sql:31` (alter table public.profiles add column total_xp). The only constraint is CHECK (total_xp >= 0). Also week_xp >= 0 (32), week_start must be a Monday (33) and streak_weeks >= 0 (34). There is no upper bound and nothing derives the value server-side.
- **propagation**: `supabase/migrations/20261104120000_leaderboard.sql:116` (public.leaderboard players CTE). week_xp counts in full when week_start equals the current UTC Monday. total_xp (115) is taken as stored, and the streak (117) is taken as stored whenever week_start >= monday - 7, which a future Monday also satisfies.
- **sink**: `supabase/migrations/20261104120000_leaderboard.sql:134` (public.leaderboard ranked CTE). row_number() orders by the client-written score and streak. The top N (at most 100, lines 101 and 148), with the attacker-chosen shown_name (114), is returned to every authenticated caller.

### Evidence
- `supabase/migrations/20261104120000_leaderboard.sql:23`: Migration comment: 'Honest limit: XP is client-reported. The check constraints keep it sane, not true; a server-side recount from mission_attempts is a later step.'
- `supabase/migrations/20261104120000_leaderboard.sql:38`: grant insert (leaderboard_visible, total_xp, week_xp, week_start, streak_weeks) on public.profiles to authenticated.
- `supabase/migrations/20261104120000_leaderboard.sql:101`: The board size is clamped to 1-100, so about 100 inflated rows push every legitimate player off the visible board.
- `supabase/migrations/20261104120000_leaderboard.sql:153`: leaderboard() is revoked from anon and granted to authenticated, so every guest and every linked account reads the manipulated ranking.
- `supabase/migrations/20261030170650_sync_profile_and_attempt_picks.sql:14`: first_name, shown as the board's display name, is player-chosen and bounded only to 1-40 characters.
- `supabase/tests/leaderboard.test.sql:49`: The only rejected-value tests are negative XP (49-53) and a non-Monday week_start (55-59). No test bounds large values. The 99999 write at line 70 fails only because it targets another user's row.
- `apps/mobile/lib/core/backend/supabase_backend.dart:104`: The app sends its leaderboard report as a plain PostgREST upsert on profiles (onConflict user_id). No server component recomputes it, so a hand-crafted request looks the same as the app's.
- `docs/completion.md:33`: Docs: 'XP is client-reported: the device sends its engine totals and the server ranks them as given... Needs the migration on the hosted project.'

### Blockers
- The decisive behaviour could not be observed locally in this run, because target code may not be executed. psql, pg_prove and deno are absent, the Supabase images are not pulled, the host has no OS-enforced sandbox (sandbox-exec cannot cap memory, processes or disk) and the promotion allowlist is empty. So the pgTAP demonstration (a dummy guest writes total_xp = 2147483647 and a second dummy user sees it ranked first) was not run, and no artifact could be promoted.
- Whether the hosted project is exposed depends on whether 20261104120000_leaderboard.sql has been applied there. docs/completion.md:33 says it 'Needs the migration on the hosted project', and that is a deployment fact not visible in source.

### Resolution plan
- **Local, sandboxed, with dummy data:** In a sandboxed local Supabase stack with no external network (supabase db reset with the repo migrations, then supabase test db), add a pgTAP case to supabase/tests/leaderboard.test.sql after the existing setup, raising plan(22) to plan(24). Then run: select lives_ok($$ execute upsert_board('Zed', true, 2147483647, 2147483647, pg_temp.monday(), 32767) $$, 'unbounded XP accepted'). Next, pg_temp.act_as('cccccccc-0000-4000-8000-00000000000c') and run: select results_eq($$ select display_name from public.leaderboard('week') where rank = 1 $$, $$ values ('Zed'::text) $$, 'inflated row ranks first for another player'). The test runs inside the file's existing begin/rollback, so it is non-destructive. Stop at that single row.
- **Owner-observed, read-only:** The owner confirms in the hosted Supabase dashboard (Database > Migrations, or the profiles table columns) whether 20261104120000_leaderboard.sql is applied. They also note whether anonymous sign-ins are enabled, the per-IP anonymous sign-in limit and the captcha setting, which set how many board rows one actor can cheaply create. This is read-only owner observation; send no audit traffic to the deployment.

## 2. Unbound thelastroom://auth-callback deep link accepts an injected access_token session and merges the victim's local progress into the attacker's account

**Fingerprint:** `apps/mobile:supabase_flutter-detectSessionInUri-implicit-token-deeplink-session-injection`

The app registers the custom scheme thelastroom://auth-callback on Android, in an exported MainActivity VIEW/BROWSABLE filter, and on iOS through CFBundleURLSchemes. It calls Supabase.initialize with detectSessionInUri left at its default (true) and no detectSessionInUriPredicate. In pinned supabase_flutter 2.18.3 (pub-cache lib/src/supabase_auth.dart:218-229 and 302-307), _defaultIsAuthCallbackDeeplink accepts any link that has access_token, code or error* in the query or fragment, and _handleDeeplink passes it to auth.getSessionFromUrl. In pinned gotrue 2.27.3 (pub-cache lib/src/gotrue_client.dart:1012-1066), PKCE only throws when access_token is absent. With access_token, expires_in, refresh_token and token_type present, the library calls getUser(accessToken), saves the session it was given (_saveSession) and emits AuthChangeEvent.signedIn. No state, nonce or code_verifier ties the link to a sign-in this device started. The attack runs in four steps. (1) The attacker gets an access/refresh token pair for their own non-anonymous, email-bearing account in the same project. This is cheap: enable_signup and anonymous sign-ins are on, and config.toml has no captcha. (2) The attacker makes the victim's device open thelastroom://auth-callback#access_token=A&refresh_token=R&expires_in=3600&token_type=bearer. A co-installed Android app can send a VIEW intent with no permission. A tapped web or message link also works, perhaps behind an OS prompt. (3) SupabaseBackend._onAuthState sees a signedIn for a non-anonymous user with a different id and a linked email, and emits AccountLinkSignedIn. (4) SaveProgressController, listening for the app's lifetime from main.dart, runs prepareAccountMerge and then switches the app session to the attacker. The merge queues every local attempt. pullAccountMerge then queues the device profile (first_name, experience, target_role, nerves_level, ...) when the attacker's account has no profile, plus the leaderboard report. SyncWorker uploads all of it under the attacker's JWT, so the attacker can read it through owner-only RLS on their own account. The victim's previous session, guest or linked, is replaced on the device, and later play keeps syncing to the attacker's uid until the victim signs out. If the attacker's token is anonymous, _onAuthState returns early and no merge runs, but the client session is still swapped silently. Every step except on-device URI delivery is readable in source. Nothing was executed.

**Claimed root cause:** SupabaseBackend._initialise calls Supabase.initialize without detectSessionInUriPredicate and without detectSessionInUri:false. In the pinned gotrue, the PKCE flow does not reject implicit-style access_token callbacks, so the custom-scheme handler, which is non-exclusive and exported, installs an unsolicited session chosen by the attacker. The app then treats any non-anonymous signedIn for a new uid as a 'sign in on another device' the user started. It never checks that a sign-in link was pending (AccountFlow mode/step or a stored nonce) before running the account merge and uploading local data.

### Source trace
- **entrypoint**: `apps/mobile/android/app/src/main/AndroidManifest.xml:50` (MainActivity (android:exported="true" at line 24) VIEW/DEFAULT/BROWSABLE intent filter). Declares scheme thelastroom, host auth-callback. Any installed app or tapped browser link can deliver thelastroom://auth-callback with any query or fragment. iOS registers the same scheme at apps/mobile/ios/Runner/Info.plist:84.
- **propagation**: `apps/mobile/lib/core/backend/supabase_backend.dart:271` (SupabaseBackend._initialise). Supabase.initialize(url, publishableKey, debug:false) sets neither authOptions nor a predicate. detectSessionInUri therefore defaults to true (supabase_flutter flutter_go_true_client_options.dart:35), the deep-link observer starts, and every link with access_token, code or error* goes to getSessionFromUrl.
- **propagation**: `pubspec.lock:385` (gotrue 2.27.3 (supabase_flutter 2.18.3 at pubspec.lock:1035)). In the pinned gotrue, getSessionFromUrl throws the PKCE error only when access_token is missing. When it is present, the method calls getUser(accessToken), _saveSession(session) and notifyAllSubscribers(signedIn), with no state or verifier binding (pub-cache gotrue_client.dart:1012-1066).
- **propagation**: `apps/mobile/lib/core/backend/supabase_backend.dart:294` (SupabaseBackend._onAuthState). A signedIn for a non-anonymous user whose id differs from _lastUserId and whose linkedEmail is non-null is emitted as AccountLinkSignedIn (line 307). Nothing checks that this device requested a sign-in link.
- **propagation**: `apps/mobile/lib/features/settings/account/save_progress_controller.dart:473` (SaveProgressController._signedIn, reached from _onLink. The listener is subscribed at line 193 and kept alive for the app's lifetime by main.dart:93). For a different uid it runs accountDevicePrepProvider (prepareAccountMerge), then makes the injected session the app session (line 475).
- **propagation**: `apps/mobile/lib/core/sync/account_merge.dart:61` (prepareAccountMerge / pullAccountMerge). Every local attempt is queued for upload. pullAccountMerge queues the device profile when the account has none (line 89) and the leaderboard report (line 94).
- **sink**: `apps/mobile/lib/core/sync/sync_worker.dart:136` (SyncWorker._flushOnce). Attempts, then profile and leaderboard rows (lines 137-138), are sent through the Supabase client holding the injected session, so they are stored under the attacker's uid, where owner-only RLS lets the attacker read them.

### Evidence
- `apps/mobile/lib/core/backend/supabase_backend.dart:291`: The doc comment assumes every signedIn for a new non-anonymous user is 'a sign-in link exchanged by supabase_flutter'. Nothing restricts which URL shape produces it.
- `docs/status/67.md:14`: The author's library review covers only the code/error* (PKCE exchange) branch of detectSessionInUri. It does not consider the access_token branch, which bypasses PKCE.
- `apps/mobile/lib/core/backend/remote_rows.dart:166`: The profile row the merge uploads: first_name, experience, target_role, nerves_level, calm_mode, weekly_goal.
- `apps/mobile/lib/core/backend/remote_rows.dart:95`: The attempt row the merge uploads: attempt_id, mission_id, picks, scores, voice_answer summary.
- `supabase/config.toml:188`: enable_anonymous_sign_ins = true, and enable_signup = true (line 186). The [auth.captcha] block is commented out (line 224). An attacker can cheaply get a valid non-anonymous access/refresh token pair in the same project.
- `apps/mobile/lib/core/backend/supabase_backend.dart:61`: linkedEmail returns the email for any non-anonymous user, so an attacker's ordinary email account passes the session.isLinked gate in _onAuthState.

### Blockers
- Target code may not be executed in this run. The host has no OS-enforced sandbox (no memory, process or disk caps), Flutter and the emulator are not permitted, and no trusted promotion tool exists. The end-to-end session swap and merge upload were therefore not observed.
- The library behaviour is source-read from the pinned packages in the local pub-cache, which lie outside the repository: gotrue-2.27.3/lib/src/gotrue_client.dart:1012-1066 and supabase_flutter-2.18.3/lib/src/supabase_auth.dart:218-229,302-307. Whether a release build on Android and iOS delivers a fragment-bearing custom-scheme URI through app_links unchanged, including on a cold start before the lazy Supabase.initialize completes, is a device and runtime fact that needs on-device confirmation.
- How the URI is delivered is a platform fact. A co-installed Android app can fire the exported VIEW intent without consent. From a browser or messaging app, a user tap is needed and the OS may show an 'Open in app?' prompt.

### Resolution plan
- **Local, sandboxed, with dummy data:** Use an Android emulator with a local Supabase stack (supabase start, dummy users only, no hosted project). (1) Create a dummy 'attacker' user with a confirmed email in the local GoTrue and record its access_token and refresh_token. (2) Install a debug build pointed at the local stack (--dart-define SUPABASE_URL/SUPABASE_ANON_KEY for the local instance only). Play one mission as a guest and note the guest uid. (3) Run `adb shell am start -a android.intent.action.VIEW -d 'thelastroom://auth-callback#access_token=<A>&refresh_token=<R>&expires_in=3600&token_type=bearer'`. (4) Observe whether auth.currentUser.id becomes the attacker's uid, whether the 'account link opened' and 'account signed in' log lines appear, and whether a mission_attempts row carrying the guest's attempt_id appears with user_id = the attacker uid in the local DB, plus a profiles row if the attacker had none. Stop there. (5) Control: repeat with thelastroom://auth-callback?code=<random> and confirm that PKCE rejects it (AccountLinkRefused). Regression test for the fix: with detectSessionInUriPredicate set to (uri) => uri.queryParameters.containsKey('code') || an error param, the access_token link is ignored, and _onLink acts only while a sign-in link is pending (AccountFlow mode signIn and step linkSent, or a stored pending-link nonce).
- **Owner-observed, read-only:** The owner confirms, without any live probe, that the released APK/IPA is built from this pubspec.lock (supabase_flutter 2.18.3, gotrue 2.27.3) with no authOptions override, and that the published Android build still exports MainActivity with the thelastroom://auth-callback VIEW/BROWSABLE filter after manifest merge.

## 3. Gemini daily quota is counted per anonymous uid, which anyone can mint, so the shared free-tier Gemini key can be rate-limited for all players

**Fingerprint:** `supabase/functions/claim_ai_score:per-uid-quota-escapable-via-anonymous-uids`

public.claim_ai_score() gives each auth.uid() 30 AI scores per UTC day. The counter itself is sound: one atomic INSERT ... ON CONFLICT DO UPDATE ... WHERE used < 30, a constant limit held in SQL, the day taken from server now() in UTC, and no write grant on ai_score_usage. But anonymous sign-in is enabled with no captcha (config.toml:188, captcha block commented at 223-226), so any client can mint a fresh authenticated uid that starts at zero. The only source-visible bound on new uids is the per-IP anonymous sign-in rate limit, which is 30 per hour in the local config.toml:213. The hosted value is not in source, and a per-IP limit can be rotated. The text and voice functions both claim the same single unit once per request, before Gemini is called (score/handler.ts:72, score-voice/handler.ts:82). Each unit can then trigger up to 3 generateContent calls, because scoreWithFallback and scoreVoiceWithFallback move to the next model on any UpstreamError or OutputError. That includes timeouts and non-OK statuses such as a 429. A voice unit also carries up to two 4,000,000-byte clips, yet costs the same unit as a short text score. From one IP, an attacker can therefore keep minting about 30 uids per hour, each with 30 units per day. That is up to about 720 uids, 21,600 units and roughly 3x that many upstream calls per IP per day, all on the operator's single GEMINI_API_KEY, and nothing in source sets a global or per-IP Gemini budget. The repository documents that the key is on Gemini's free tier, with per-model rate limits (docs/ai-reliability-and-cost.md:48). Because the fallback chain retries on 429 across all three models, sustained abuse would use up every model's shared limit. AI scoring would then stop for every player until the provider window resets; the app degrades to the offline score and nothing else breaks. On a paid key, the same path becomes operator spend. The actual impact depends on the hosted anonymous sign-in limit, on captcha, on any edge/WAF limits and on the key's tier and limits, none of which can be seen in source.

**Claimed root cause:** The AI quota's accounting dimension is auth.uid() alone (claim_ai_score, daily_limit 30), while uids are minted free by anonymous sign-in with no captcha, bounded only by a per-IP hosted auth rate limit. No global or per-IP Gemini budget exists in source, voice scores are not cost-weighted, and the model fallback chain makes up to 3 upstream calls per claimed unit.

### Source trace
- **entrypoint**: `supabase/config.toml:188` (auth). enable_anonymous_sign_ins = true: any client can mint an authenticated uid via signInAnonymously; captcha is not configured (the [auth.captcha] block at lines 223-226 is commented out).
- **propagation**: `supabase/config.toml:213` (auth.rate_limit). anonymous_users = 30 per hour per IP is the only source-visible bound on minting new uids (local config; the hosted value is not visible).
- **propagation**: `supabase/functions/score/handler.ts:72` (handle). One claimQuota(jwt) per request (POST rpc/claim_ai_score as the caller, index.ts:37), made before Gemini is called; score-voice/handler.ts:82 claims the same counter.
- **propagation**: `supabase/migrations/20261031130000_ai_scores.sql:95` (claim_ai_score). Atomic upsert keyed on (caller uid, UTC day), capped by daily_limit 30 (line 88). A freshly minted uid starts with a full 30.
- **propagation**: `supabase/functions/score/gemini.ts:153` (scoreWithFallback). Loops over GEMINI_CHAIN (3 models, lines 34-36) and falls through on any UpstreamError/OutputError, including timeouts and non-OK statuses such as 429, so one claimed unit makes up to 3 upstream calls.
- **sink**: `supabase/functions/score-voice/gemini_voice.ts:79` (scoreVoiceWithGemini). Gemini generateContent with the operator's GEMINI_API_KEY and the player's audio (up to two 4 MB clips); it is reached up to 3 times per unit through scoreVoiceWithFallback (line 124).

### Evidence
- `supabase/migrations/20261031130000_ai_scores.sql:88`: daily_limit constant integer := 30, applied per caller uid only; no global or per-IP Gemini budget appears anywhere in source.
- `supabase/functions/score-voice/voice.ts:68`: MAX_AUDIO_BYTES = 4_000_000 per clip (two clips per request, MAX_BODY_BYTES 12 MB at line 71), still one quota unit.
- `supabase/functions/score-voice/gemini_voice.ts:17`: VOICE_CHAIN reuses the 3 GEMINI_CHAIN models with timeouts of 11/9/7 s, so a fully failing voice unit makes 3 calls in about 27 s.
- `apps/mobile/lib/core/backend/guest_sign_in.dart:16`: The app comment treats Supabase's 30 anonymous sign-ins per hour per IP as the bound on guest creation.
- `docs/decisions/0006-ai-scoring.md:42`: The design names the 30-a-day per-player limit as the cost control, which assumes one uid per player.
- `docs/ai-reliability-and-cost.md:48`: States the key is on Gemini's free tier, whose per-model rate limits the fallback chain absorbs. Exhausting those limits therefore affects every player, and voice token cost has not been measured.

### Blockers
- No target code may be executed in this run (no OS-enforced sandbox with resource caps; deno, psql and pg_prove are absent; the promotion allowlist is empty), so the per-uid reset and the 3x fallback amplification cannot be observed locally.
- The hosted Supabase project's anonymous sign-in rate limit, captcha setting and any edge/WAF or per-function request limits are deployment facts that are not visible in source, and they decide the attacker's real uid-minting rate.
- The Gemini key's current tier and its per-model RPM/RPD/TPM limits are provider facts outside the repository, and they decide whether the impact is shared availability loss or operator spend.

### Resolution plan
- **Local, sandboxed, with dummy data:** Inside an OS-enforced sandbox with no network and a local `supabase start` stack: (1) with pgTAP, set request.jwt.claims to two distinct dummy uids in turn and call public.claim_ai_score() 31 times each; expect true 30 times and then false for each uid independently. (2) With a Deno unit test, call scoreVoiceWithFallback and scoreWithFallback with an injected fetch that always returns a 429 Response (and, separately, one that never resolves so it aborts on timeout), and assert the fake fetch was called exactly 3 times for a single invocation, i.e. for a single claimed unit.
- **Owner-observed, read-only:** The owner, without sending any audit traffic, checks in the Supabase dashboard: Authentication > Rate Limits (the anonymous sign-ins per hour per IP value), Authentication > Attack Protection (whether captcha is enabled), and any edge or WAF limits in front of the functions. In Google AI Studio they check the GEMINI_API_KEY project's tier and its per-model RPM/RPD limits for gemini-3.5-flash-lite, gemini-3.6-flash and gemini-3.1-flash-lite. Then compare (anon uids per IP per hour x 24 x 30 units x up to 3 calls) against those limits to see whether one IP can exhaust the shared daily quota.

## 4. score reads a JSON body with no size cap, and score-voice fully buffers a chunked body, before the caller's identity is validated

**Fingerprint:** `supabase/functions/handler:unbounded-body-buffering-before-jwt-validation`

Both Edge Function handlers check only that an Authorization header has the shape 'Bearer <non-space>' (score/handler.ts:47-59, score-voice/handler.ts:41-63). They then read and parse the whole request body before the first identity check, which is the PostgREST rpc/claim_ai_score call made with the caller's token (score/handler.ts:72, score-voice/handler.ts:82; score/index.ts claimQuota maps 401/403 to Unauthorized). In score, req.json() at handler.ts:63 has no size cap. The 600-character field caps (scoring.ts:57) apply only after the full body has been buffered and parsed. In score-voice, the 12,000,000 cap (voice.ts:71) is checked against the Content-Length header, and a missing header becomes 0 (handler.ts:65). req.text() at handler.ts:73 then buffers the entire body before checking raw.length at :74. That check measures UTF-16 code units, not bytes. Only after it do JSON.parse and the base64 regex checks run (voice.ts:137). The source also shows that even if the platform's verify_jwt check is on, it does not stop a caller who has no session. The public anon key is itself a valid project JWT, so it passes the gateway and still reaches the buffering step. That caller is then rejected only at claimQuota, because all grants are revoked from anon. So a caller with only the public anon key, a junk bearer string (if verify_jwt is off), or a free anonymous-guest JWT can make each invocation buffer and parse a body as large as the platform lets through. That uses isolate memory and CPU and the operator's function invocations and compute, with no quota unit spent. How large a body can actually get through depends on the Supabase Edge gateway's request-size limit and per-isolate memory and CPU limits. Those are platform facts that are not in the repository. The verifier could not run target code to observe the buffering.

**Claimed root cause:** The score handler has no body-size gate at all. The score-voice gate only checks the Content-Length header and treats a missing header as 0. In both handlers the full body is buffered and parsed after a presence-only bearer check and before the caller's identity is validated (claim_ai_score through PostgREST). No streaming byte limit enforces the intended cap.

### Source trace
- **entrypoint**: `supabase/functions/score/handler.ts:58` (handle). bearer() (lines 47-51) accepts any non-whitespace token after 'Bearer '. Line 59 rejects only a missing or malformed header, so the token is never validated here.
- **propagation**: `supabase/functions/score/handler.ts:63` (handle). parseInput(await req.json()) buffers and parses the entire body with no size limit, before claimQuota at line 72.
- **propagation**: `supabase/functions/score-voice/handler.ts:65` (handle). Number(req.headers.get('content-length') ?? '0'): a body with no Content-Length header (chunked) counts as 0 and passes the MAX_BODY_BYTES check at line 66.
- **sink**: `supabase/functions/score-voice/handler.ts:73` (handle). await req.text() buffers the full body before the raw.length (UTF-16 units) check at line 74 and JSON.parse at line 75. The caller's identity is first checked at claimQuota on line 82.

### Evidence
- `supabase/functions/score/handler.ts:72`: The first identity validation (deps.claimQuota(jwt) through PostgREST; 401/403 becomes Unauthorized in score/index.ts) runs only after the body has been parsed at line 63.
- `supabase/functions/score-voice/handler.ts:82`: In score-voice, the first identity validation also comes after the body is fully buffered and parsed (lines 73-75).
- `supabase/functions/score-voice/voice.ts:71`: MAX_BODY_BYTES = 12_000_000 is the only whole-request cap. Its comment says it is 'checked on content-length before anything is parsed', but nothing enforces it on the actual stream.
- `supabase/functions/score-voice/voice.ts:137`: The base64 length and regex checks run over each audio string only after the full body has been buffered and parsed.
- `supabase/functions/score/scoring.ts:57`: MAX_TEXT = 600 per field is enforced in text() (lines 63-66) only after the whole body has been parsed.
- `supabase/config.toml:402`: The [edge_runtime] section sets no [functions.score] or [functions.score-voice] verify_jwt, and no repository script or workflow passes --no-verify-jwt. Whether the gateway rejects invalid JWTs before the handler is therefore a deployment fact.

### Blockers
- No target code may run in this run: there is no OS-enforced sandbox, deno is absent, and the promotion allowlist is empty. So it cannot be observed locally that a chunked or oversized body is fully read before the 401/400/413.
- Whether the hosted score and score-voice functions run with the platform default verify_jwt=true is a deployment fact. If it is on, a junk bearer string is rejected at the gateway, but the public anon key and free anonymous-guest JWTs still reach the buffering step, so this narrows the attacker but does not remove the path.
- The Supabase Edge gateway's maximum request-body size and its per-isolate memory and CPU or wall-clock limits are platform facts outside the repository. They decide whether the buffering is bounded to an acceptable size or can exhaust the isolate.

### Resolution plan
- **Local, sandboxed, with dummy data:** In a Deno sandbox with no network, a read-only target, scratch-only writes and a memory cap such as --v8-flags=--max-old-space-size=128, import handle() from supabase/functions/score/handler.ts and supabase/functions/score-voice/handler.ts. Give each a fake Deps whose claimQuota records that it was called and throws Unauthorized, and whose score and saveScore throw if called. Send each a Request with method POST, header 'authorization: Bearer x', no content-length header, and a ReadableStream body of 2 MB of '{"a":"' + 'x'.repeat(n) + '"}'. A counter in the stream records how many bytes were pulled. Expected source-predicted result: score pulls the whole 2 MB and returns 400 (invalid_request) or 401. score-voice pulls the whole 2 MB before returning 400 or 401. In neither case does the counter stop near a cap. Repeat score-voice with a 13 MB stream and no content-length: it is fully pulled before the raw.length 413.
- **Owner-observed, read-only:** The owner, without sending any audit traffic, checks two things. First, in the Supabase dashboard under Edge Functions settings for score and score-voice, whether 'Enforce JWT verification' (verify_jwt) is enabled, or whether either function was deployed with --no-verify-jwt. Second, the project's documented Edge Functions limits for maximum request size and per-invocation memory and CPU time. If the gateway allows bodies much larger than about 16 KB for score or 12 MB for score-voice, the fix is a streaming byte counter on req.body that cancels and returns 413 once the per-function cap is exceeded, before any parse. The counter should apply whether or not Content-Length is present. Ideally the caller's token is also validated (for example with auth.getUser or the quota claim) before the body is read.
